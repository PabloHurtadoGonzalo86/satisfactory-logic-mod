# Lecturas del implementador de C++ (13-oct-2026)

Estado: registro histórico. Lo escribió el agente que implementó `core/` leyendo solo `docs/spec`, **sin ver el oráculo ni los tests**, antes de que se compararan. Es la otra mitad de la evidencia de [ambigüedades.md](ambiguities.md): donde las dos lecturas coincidieron, la especificación quedó confirmada; donde difirieron (B2, B4, B8), manda el oráculo y el C++ se alinea. El texto es el del informe original, sin editar salvo rutas locales.

## Desviaciones y decisiones sobre la API

- Header and source layout: the spec text says 'core/host/' for slg::host. Per the task ownership the headers are core/include/slg/host/{step_pacer,frame_driver,fullness}.hpp and the sources core/src/host/*.cpp. The root Makefile's LIB_SRC uses a recursive find over core/src and core/host, so all 10 .cpp files are picked up.
- API additions that 02 section 2 does not list (all additive, none changes a listed signature): Netlist(Limits = {}) constructor, Netlist::limits(), Netlist::newBatch(); EditBatch(ComponentId baseNextId = 1) explicit constructor plus baseNextId(), size(), empty() (the spec shows no way to build a batch without a Simulator, and Netlist::apply needs Limits); StepPacer::accumulatedMicros(), stepMicros(), maxStepsPerCall() (G12 checks acc = 10000 but the spec lists no accessor for it); slg::host::kUnconfirmed (= 0xFF); slg::detail::Slot, an implementation struct that sits in the public simulator.hpp so that Simulator's members can be vectors of it.
- Signatures the spec leaves open, chosen here: makeConst(uint16_t), makeGate(GateOp, bool, uint16_t), makeDelay(uint16_t), makeClock(uint16_t period, uint16_t high); Signal fullness(std::int64_t num, std::int64_t den) noexcept with exact integer arithmetic (no 14*num product, so no overflow; checked against 128-bit arithmetic over 220000 pairs); Simulator(Limits limits = {}, uint32_t hostStepMicros = 0) takes Limits by value; Netlist::apply validates Spec parameters but not seeds (the '(seeds ignored)' comment), while Simulator::apply validates both.
- No Wire/FeedbackReport/ActuatorChange comparison operators were added beyond the ones the spec declares (Pin <=>, Spec ==).
- The FrameDriver blob has a layout I had to design (see ambiguities). Version constants and magics are internal to the .cpp files, not public API.

## Ambigüedades halladas

- A1 validate() status split (CONFLICTS with docs/spec/ambiguities.md B2; that file was read only after the code was written and the code was NOT changed to match). My rule: intrinsic malformation (arity 0, d 0, P < 2, H outside 1..P-1, op > 2, inv > 1, mode > 1, Const v > 15, unused param != 0, seed out of domain) is BadSpec. A parameter over its Limits field is LimitExceeded, except when it is also past the catalog range (arity 8, d 255, P 4096) and the limit is at or below that range; then it is BadSpec. So with default limits Delay(256), Gate arity 9 and Clock period 4097 are BadSpec; with Limits{maxDelay=4} Delay(5) is LimitExceeded; with a raised limit anything up to the limit is accepted. The oracle (B2) reads every Limits field as the sole upper bound, so d=256 at default limits is LimitExceeded there. A decode of a blob with Delay(256) gives FormatCorrupt here and LimitExceeded in the oracle. One-line switch: classifyUpper() in core/src/internal/spec_rules.cpp.
- A2 Const and Sensor have no seed domain row in 01 section 6.1: I accept only seed 0 and return BadSpec otherwise (oracle B1 agrees).
- A3 Wire/pin statuses. Order inside one op: UnknownComponent, then BadPin, then DuplicateWire. A wire with a == b is BadPin. Wires between two inputs or two outputs are legal. An Actuator has no output pin (BadPin). Disconnect (CONFLICT with oracle B4): mine returns UnknownWire for any wire that is not present, including ones naming a missing component or pin; the oracle validates the pins first (UnknownComponent / BadPin) and only then UnknownWire. Switch point: the Disconnect case in Netlist::applyInto.
- A4 Explicit ids (oracle B3 agrees). addWithId needs id >= the batch BASE nextId, not the running one, so ids may come in any order (T1/T2 rebuild with permuted ids; checked with shuffled insertion and shuffled wire order). An id < base is DuplicateId if present, else RetiredId (id 0 included). Within a batch: an id already added is DuplicateId; an id created and then removed in the same batch is RetiredId; id >= 0xFFFFFFFF is LimitExceeded. add() returns max(base, highest id so far + 1). Final nextId = max(base, highest id added + 1); it never moves down even if that component is removed later in the batch. StaleBatch applies to any base mismatch, including an empty batch (Simulator::apply with an empty batch returns Ok only when the base matches).
- A5 Limits are judged on the FINAL netlist of a batch (components, wires, total Delay cells, pins per net), not per operation (oracle B5 agrees). Exception: add with nextId already 0xFFFFFFFF is LimitExceeded immediately. maxNetPins counts every pin of a connected net, which equals the distinct pins appearing in wires. Decode difference (oracle B8): I check the Delay-cell total while reading components, the oracle checks it at the end, so a blob that exceeds the cell limit AND is corrupt later can return a different status.
- A6 Decode order: need >= 4 bytes and magic; need >= 8 for versions; version above 1 in either field is FormatTooNew before looking at anything else; version 0 in either field is FormatCorrupt (oracle B7 agrees); then length >= 40; then the FNV tail; then counts (limit first -> LimitExceeded, then bytes left -> FormatCorrupt); ids must be 1..0xFFFFFFFE and strictly ascending; nextId >= 1 and above every id; params via validateParams (LimitExceeded passes through, BadSpec becomes FormatCorrupt); states in domain; wires normalized (a < b), strictly ascending, both pins existing; no extra bytes; then net pins. 'out' is only replaced on Ok.
- A7 Lint report shapes. groups: SCCs of the net-induced graph with 2+ components or one component that reads a net it also drives (self edge); ids ascending within a group, groups ordered by smallest id. undrivenInputs: every input pin whose net has no output pin (unwired pins included), in ascending (id, index). multiDriverNets: every pin of the net (inputs and outputs), ascending, nets ordered by their smallest pin, only nets with >= 2 output pins. The spec does not say whether the vector holds only the conductors or every pin. settlingBounds: one entry per actuator in ascending actuator id; nullopt when any ancestor is in a feedback group or is a Latch, Toggle or Clock.
- A8 Pulse sensors (CONSISTENT with oracle B9, but in tension with the wording of 02 7.4 'si no, el pulso se repetiría'): a Pulse sensor reads its offered value in the FIRST step of a call and 0 afterwards; in a call with no offer it reads 0 in every step. Only that reading makes both 'three one-step calls end in the same X3' (7.2) and 'Pulse differs by design' (T13) true when the reading is offered once. A Level sensor keeps its last good value when nothing is offered. A Pulse's retained value is therefore never used, and it is persisted as 0.
- A9 Unresolved sensors: all sensors are unresolved when a FrameDriver is constructed, when its blob is decoded, and when a sensor is created through FrameDriver::apply. changes() stays empty (the steps still run) while any sensor is unresolved. A sensor is resolved by its first offer or when its own waited time reaches resolveTimeoutMicros. 'Waited time' is the sum of the elapsedMicros passed to runCall; since 02 7.1 has the adapter skip runCall when pacer.advance gives 0 steps, the timer UNDER-counts real time, so the 5 s timeout is really 5 s of dt summed over the calls that actually ran. Open point for the adapter/spike.
- A10 Settle guard: after a FrameDriver::apply that succeeds with a non-empty batch, EVERY actuator whose settlingBounds is defined holds its deliveries for L_a simulator steps (not calls), counted down by the steps run; actuators with no bound get no hold; settleGuard=false disables it. I could not tell whether the guard should apply only to actuators whose cone the batch touched. Checked: sensor 15 -> NOT -> NOT -> actuator, all born at rest, one-step calls: 0 deliveries with the guard, 2 (15 -> 0 -> 15) without it.
- A11 FrameDriver edge semantics: a created actuator starts with confirmed = its current o (nothing is written at creation); ActuatorChange::previous is kUnconfirmed (0xFF) after resync() or when never acknowledged; acknowledge() only has an effect inside a call (between runCall and endCall) for an actuator listed in the current changes(), and does not modify changes() (so iterating changes() while acknowledging is safe); an unacknowledged change is offered again next call; runCall while already in a call returns WrongPhase (the spec only names apply); offer/setSensorMode for an unknown id are ignored; runCall(0, dt) runs no steps, keeps pending offers for the next call, still advances the unresolved timers and still produces changes(); offers and sensors created directly through Simulator::apply (not via the driver) are picked up by reconciling against the simulator at every runCall/apply/offer/setSensorMode/resync (tracked by structureHash).
- A12 FrameDriver blob layout is NOT specified beyond '(versión propia; por sensor u32 id, valor retenido y modo; por actuador u32 id y valor confirmado o 0xFF; cola FNV-1a)'. Mine: magic 53 4C 47 44 'SLGD'; u16 version = 1; u32 sensorCount; u32 actuatorCount; per sensor u32 id, u8 retained, u8 mode (0 Level, 1 Pulse); per actuator u32 id, u8 confirmed (0..15 or 0xFF); u64 FNV-1a tail. Pulse sensors are written with retained = 0 and decode rejects a Pulse with a nonzero retained value, so encode(decode(b)) == b for every accepted blob. A Level's retained byte is any value (raw readings above 15 are kept and clamped/counted by Simulator::step). decode requires the id sets to equal the simulator's exactly (FormatCorrupt otherwise) and leaves the driver untouched on any failure; tests cannot hand-craft this blob.
- A13 clampedSamples counts every out-of-range sample at every step, so a Level sensor holding 200 for a 3-step call adds 3. A BadFrame step does not touch the counter (I3).
- A14 StepPacer: arithmetic is 64-bit internally; 'acc' is kept untouched during a pause; stepMicros and maxStepsPerCall are clamped to >= 1; droppedSteps and pausedMicros are 64-bit.
- A15 EditBatch semantics of replace: kind may change; every wired pin must exist in the new spec at that point of the batch (BadPin otherwise); state resets to the seed (Toggle gets p = 1); the id and wires are kept. A batch is judged in op order, so replace-then-disconnect of an invalid pin still fails.
- A16 Spec-text tension noticed (no code consequence): 03 T12 'cada límite excedido da LimitExceeded' reads as the pure Limits rule, while 01 section 6.1/catalog ranges 'd 1..255' read as BadSpec; see A1. Also 03 5 says the oracle sees only 01 and 03, but the codec is defined in 02 (the oracle log already notes it).
